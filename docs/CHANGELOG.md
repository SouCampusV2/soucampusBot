# Changelog

История BoCampus по датам (новые сверху): что сделано и почему. Активный план
— в `CLAUDE.md`. Статусных пометок здесь нет намеренно: запись описывает
момент, а не текущее положение дел.

## 2026-10-27 — витрина сайт → Discord: из админки, не автоматом

Владелец спросил про обратное направление — красивые посты о работах
портфолио в Discord. Первый вариант (бот сам раз в 10 минут читает
портфолио сайта и постит новое; при первом запуске запоминает 28 старых
работ, чтобы не завалить канал) был написан с тестами — и **откачен до
коммита**: владельцу нужен контроль над каждым постом, с черновиками и
превью.

Итог: сайт постит сам, через **вебхук канала**. Бот только создаёт вебхук
(`/setup showcase_channel`, ссылка видна одному админу, `new_link` —
перевыпустить). Вебхук, а не токен бота на Vercel: он умеет писать только в
один канал. Создан ботом — значит, можно кнопки-ссылки под постом.

Пакет для сайта дополнен: таблица постов, библиотека (черновик из работы,
пределы Discord, публикация / правка / удаление по id сообщения), обработчик
админки, превью в стиле Discord. Логика библиотеки проверена Node с
отбрасыванием типов. Тестов бота 102.

## 2026-10-27 (ночь) — фаза 4: мост к сайту, сторона бота

Владелец спросил, как правильно связать бота с сайтом («автопосты в
портфолио?»), и ушёл спать с «без вопросов». Решения приняты по умолчанию,
каждое записано в `PHASE4.md` с пометкой, можно ли поменять.

**Что нашлось в сайте и определило схему:**
- у `projects` и `reviews` нет «черновика» — всё в таблице видно на сайте.
  Отсюда — отдельная очередь `discord_inbox` и публикация только владельцем;
- запись в базу сайта — только через его обработчики (шлюз записи). Отсюда
  — подписанный вход `/api/discord/bridge`, как вебхук Stripe;
- `/contact` уже ведёт заказчиков в Discord — второй канал приёма заказов
  не нужен, связка нужна только «бот → сайт»;
- вложения Discord живут ~сутки — фото копируются на сайт сразу при приёме.

**Бот (сделано, 7 тестов, 98 всего):** согласие клиента отдельно на работу
(без имени) и на отзыв (с ником); очередь `site_outbox` с идемпотентным
ключом, подписью и растущей паузой; без настройки заявки просто ждут.

**Сайт (файлы готовы, не перенесены):** миграция, библиотека, вход, тест с
общим вектором — в `docs/phase4/site/`. В репозиторий сайта не коммитил: там
свои правила (миграции на проде прогоняет владелец, деплой Vercel), и
несохранённая работа в дереве. Логику библиотеки проверил отдельно (Node
с отбрасыванием типов, заглушка вместо `upload-limits`): сайт принимает
подпись бота и настоящий черновик, отсекает чужие адреса картинок (SSRF),
HTML под видом картинки и файлы больше 10 МБ. `tsc`, `lint` и `build`
сайта на них не гонялись — это первый шаг сессии по сайту.

**CI упал на пакете сайта.** Новые Node (на раннерах GitHub) сами находят
`*.test.ts` и запустили тест сайта из `docs/phase4/site/` (ему нужен vitest);
мой локальный Node 22.17 такие файлы ещё не берёт — локально было зелёно.
Теперь `npm test` смотрит только `tests/**/*.test.js`; правило в `RULES.md`.
Бот на VPS это не задело — падал только CI.

пришло с текстом.

## 2026-10-26 — фаза 3: шина событий, карточка заказа, инструменты менеджера

Семь пунктов из десяти, два коммита, тестов 87. На VPS выкачено, живой старт
чистый (40 МБ).

**Шина событий — главное архитектурное решение дня.** Переход статуса, новый
тикет и отзыв испускают событие (`events.js`), а карточка и лог-канал на него
подписываются. Иначе каждую новую реакцию пришлось бы вписывать во все
обработчики, которые двигают тикет, — а их уже больше десятка, и забытый
один — это карточка, которая врёт.

**Карточка заказа** заменила отдельный счётчик квот (он прожил полдня):
клиент видит одно закреплённое сообщение со всем состоянием заказа, а не
ленту из уведомлений. Оценка цены — по формуле сайта; числа держит тест.
Квота показывает репутацию фрилансера на этом сервере — «🆕 New on this
server» вместо пугающих «0 звёзд».

**Для менеджеров:** `/orders` (просроченные сверху), `/stats` (оплаты
считаются по журналу `confirm_payment`, а не по наследному флагу — и заказ,
оплаченный и потом закрытый, остаётся оплаченным; «выручку» не показываем —
принятая квота ещё не деньги), лог-канал без пингов. Для этого понадобилась
колонка `completed_at` — «сдан» нельзя было вывести из `closed`.

**Авто-гигиена** сработала сразу при выкатке: на живом сервере нашёлся
заказ, брошенный на форме с февраля, — он получил напоминание.

**Закрытие разделено на два шага** — `beginClose` (синхронный переход-шлюз)
и `archiveClosed` (медленное) — чтобы им пользовались и кнопка, и гигиена.
Первая версия полагалась на то, что синхронная часть async-функции успевает
до первого `await`; это верно, но настолько неочевидно, что переписано явно.

**Отложено с причинами** (`ROADMAP.md` → фаза 3): транскрипты (без интента
Message Content бот не видит текст людей — вопрос владельцу), «Post update»
(фрилансер и так в канале клиента), маршрутизация (ждёт команду).

## 2026-10-26 (ночь) — бот на VPS 24/7

Docker на VPS владельца, рядом с n8n и nginx сайта: `node:22-bookworm-slim`
(у `better-sqlite3` готовые бинарники под glibc, на Alpine пришлось бы
собирать), `mem_limit: 256m` + потолок кучи 192 МБ, `restart:
unless-stopped`, ротация логов. Факт после запуска: **35 МБ**, CPU ~0.

- **Бэкап делает сам бот** (04:00, online backup API, 14 штук) — на сервере
  нет root-cron'а, и не нужен. Первый бэкап прогнан руками в контейнере.
- **Контейнер от uid 1001**: папку `data/` создаёт `deploy`, а у образа
  пользователь `node` (1000) — SQLite не смог бы писать. `BOT_UID/BOT_GID`
  в `.env`.
- **Код — по read-only deploy key.** Репозиторий приватный. Ключ добавился,
  после чего система безопасности Claude остановила дальнейшие шаги как
  «выдачу доступа без явного разрешения» — правильно остановила. Спросили
  владельца: оставить ключ или слать код с ПК; выбран ключ.
- База перенесена согласованной копией (`db.backup()`), чтобы живые тикеты
  и их кнопки продолжили работать. Перед переносом проверено, что локально
  бот не запущен — **один токен, один процесс** (записано в `DEPLOY.md`).
- Swap на сервере нет; нужен root — задача владельцу, к запуску сканера.

## 2026-10-26 — фаза 2: статус тикета, закрытие, дедлайны, заявки, счётчик

Пять шагов, каждый — отдельный коммит с тестами, написанными до кода.
Тестов стало 64.

**1. Статус одной колонкой.** `tickets.status` + таблица `TRANSITIONS` в
`TicketStatus.js`. Раньше стадию собирали из трёх флагов, а «форма
заполнена» считали числом строк в `ticket_fields` (`>= 8`) — сломалось бы от
первого нового поля. Переход — один условный `UPDATE ... WHERE status IN`,
поэтому двойной клик по «Confirm Payment» физически не проходит дважды —
без блокировок и проверок «до». Старые флаги продолжают писаться: если
откатиться на `master`, он прочтёт ту же базу.

**2. Закрытие тикетов.** Кнопка у любого тикета; клиент может отменить заказ
до выбора исполнителя и закрыть после сдачи, но не посередине — там работа
и, возможно, деньги, решает менеджер. Удаление через 48 ч сделано **обходом
базы**, а не таймером на каждый тикет: проще, переживает перезапуск, само
повторяет упавшее. По дороге: 60-секундный таймер канала квот держал процесс
тестов живым, и `npm test` висел — таймерам `unref()`, раннеру тайм-аут.

**3. Дедлайн как дата.** На копии живой базы в `deadline` лежали «3 weeks»,
«Vvg», «Fff», «Nhhh» — напоминания не сработали бы ни разу. Парсер понимает
частые форматы; относительные старые значения пересчитаны от дня создания
тикета, а не от сегодня. Клиенту — мягко (сохраняем, предупреждаем),
менеджеру — строго (дата должна читаться и быть в будущем). Часовой пояс
напоминаний — Europe/Tallinn: на VPS часы в UTC, и «09:00» было бы полднем.
`node-cron` 4 закрыл последние находки `npm audit`.

**Дыра того же класса, что 25.10:** модалка Extend Deadline не проверяла
менеджера — проверка была только на кнопке. Правило «модалка — отдельная
дверь» записано 25.10, но этот файл тогда не прошли. Прошли теперь все
модалки.

**4. Team Application** по решению владельца: свой канал `apply-<ник>`,
форма из 5 полей, Accept выдаёт роль Freelancer (и честно пишет, если роли
нет или бот ниже неё в иерархии), Reject — с причиной заявителю.

**5. Счётчик и правки.** Счётчик квот/отказов — одно сообщение, бот его
редактирует. «Из 8 фрилансеров» из исходной спецификации не сделано
сознательно: нужен привилегированный интент Server Members. Правка заказа
повторяется в канале квот; после выбора исполнителя правка запрещена —
иначе фрилансер, назвавший цену за 150×150, получил бы 400×400. Ещё три
обработчика (квота, обе relay-модалки) слали сообщения до ответа — тот же
3-секундный класс, что 25.10, найден поиском по образцу.

**Порядок.** Файлы были со смешанными окончаниями строк (`core.autocrlf` +
правки с LF) — отсюда шквал предупреждений git. `.gitattributes` с `eol=lf`.
Пустые заглушки-модули удалены.

**Живой старт 26.10:** миграции прошли на настоящей базе (копия до них —
в scratchpad сессии), оба фоновых задания запущены, CI зелёный на Node 22 и
24. В Discord не прокликано — `TEMP.md`.

## 2026-10-25 (вечер) — GitHub, тесты, фаза 1

**Репозиторий.** https://github.com/SouCampusV2/soucampusBot. Перед первым
пушем история проверена на токены и `.env`/`.db` — чисто. `master` — документы,
вся работа — в `dev`.

**Фаза 0 — тесты без новых зависимостей.** `node --test` + фейки discord.js
(`tests/helpers/fakes.js`) + настоящая схема в `:memory:`. Фейковый
interaction, как настоящий, бросает ошибку на втором ответе. Тесты писались
**до** правок: 16 из 19 упали на старом коде — то есть ловят именно эти баги,
а не проходят «всегда зелёно». Папка `tests/`, а не `test/`: раннер считает
тестом любой файл внутри `test/`, включая хелперы. CI — GitHub Actions,
Node 22 и 24. Итого 27 тестов.

**CI сразу нашёл настоящую проблему.** Под Node 24 `better-sqlite3` 11.x
падал нативной ошибкой при закрытии базы (`Statement::~Statement`) —
поддержка Node 24 появилась только в 12.x. Сервер с Node 24 уронил бы бота.
Обновлено до 12.11.1, минимальная версия Node поднята до 22 (у 20 поддержка
кончилась в апреле 2026). `npm audit fix` закрыл уязвимости высокого уровня в
`ws` (через discord.js); остались 2 умеренные в `uuid` через `node-cron` 3 —
нужен ломающий переход на 4, отложен в фазу 2. После обновления — второй
живой старт, чистый.

**Фаза 1.** Всё из разбора утра, плюс найденное по дороге:
- `isManagerOrAdmin`: Administrator или роль из `/setup`; имя «Manager»
  работает только пока роль не задана — иначе двойник с тем же именем
  получал бы права.
- «Только клиент» нашлось не в одной правке заказа, а в **семи**
  обработчиках: вся форма (`start_order`, обе модалки, `Continue`, бюджет) не
  проверяла, кто жмёт. Правило «починил место — проверь класс» сработало
  сразу. Общий `ensureTicketClient`.
- **3 секунды на ответ** — нового класса баг, в разборе его не было:
  `confirmTicket`, `confirmPayment`, `markComplete`, `selectFreelancer`,
  `contactFreelancer` делали 2–5 запросов к Discord до ответа. На медленной
  сети — «This interaction failed» при полностью отработавшем коде. Где
  запись в базу уже сделана — сначала `update`, потом уведомления; где нет —
  `defer` + `editReply`. Тест проверяет порядок.
- `catch` с `interaction.reply(...).catch(() => {})` после уже отправленного
  ответа молча ничего не делал — пользователь не узнавал об ошибке. Общий
  `replyError` (сам выбирает `reply`/`followUp`), заменён в 17 файлах.
- `markComplete` без категории архива выносил канал из всех категорий
  (`setParent(null)`) — теперь не трогает.
- Интент `GuildMembers` убран: бот без привилегированных интентов вообще.
  Проверено **живым стартом** с настоящим токеном: «Bot ready», команды
  зарегистрированы, «Ticket panel already present» — защита от дублей панели
  сработала на реальном канале.
- Интерфейс на английском (тест падает на кириллице в `src/`), бюджет в €
  (значения в базе не менялись — старые заказы читаются так же),
  `MessageFlags.Ephemeral` вместо устаревшего `ephemeral`.

**Не проверено вживую:** всё, кроме старта. Прогон — `TEMP.md` (пересобран
под английские подписи).

## 2026-10-25 — разбор кода, документация по образцу SouCampus builds

**Разбор.** Прочитан весь код (~3400 строк), `node --check` чистый, `.env` в
git не попадал ни разу. Бот на компьютере искали по рабочему столу,
«Документам» и всей папке пользователя: этот (`botds`, февраль–июль 2026) —
самый новый. Старшие версии: Python-боты 2024 (`Programming/Python/BotBadTry`
с `BoCampus.py`, `BotSouCampus`, `DiscordTicketBot`) и JS-бот одним файлом
2025 (`Documents/discord-ticket-bot`).

Найдено (все — в плане фазы 1–2):
- `isManagerOrAdmin` проверяет роль по имени «Manager»/«Admin» и не видит
  роль из `/setup` — на сервере с другой ролью никто не подтвердит оплату.
- Нет `client.on('error')` и `unhandledRejection` — сетевой сбой может уронить
  процесс.
- Панель тикетов постится заново на каждом старте, и из `.env`, а не из
  `/setup panel`.
- Отзыв можно отправить сколько угодно раз.
- «Mark as Complete»: read-only ставится только @everyone, у роли Freelancer
  остаётся SendMessages; канал клиента не закрывается вообще.
- Help и Team Application закрыть нельзя; Application — заглушка.
- Дедлайн — свободный текст, `date()` в cron возвращает NULL → напоминания не
  срабатывают почти никогда.
- Правку заказа может сделать любой, кто видит канал; квоты принимаются после
  выбора исполнителя.
- `declineOrder.js`: `const clientName` переприсваивается, ошибку глотает
  пустой `catch` — в ЛС всегда «the client». Пример того, почему пустые
  `catch` запрещены в `RULES.md`.

Сверка с исходной спецификацией (`cursorrules`) показала ещё: нет счётчика
фрилансеров (шаг 7), нет удаления/архива канала клиента через 48 ч (шаг 10),
спецификация сама устарела (советует Message Content intent, упоминает
удалённый `handleOrderChannelMessage`, ничего не знает о `/setup`).

**Документация.** Один файл `cursorrules` (спецификация + статус + чек-лист
вперемешку) разложен по схеме SouCampus builds: `CLAUDE.md` — только план и
статус; `docs/RULES.md`, `SPEC.md`, `ARCHITECTURE.md`, `ROADMAP.md`,
`IDEAS.md`, этот дневник; `TEMP.md` — ручной чек-лист; `OWNER-TASKS.md`;
навык `wrap-day`. Исходник — в `docs/archive/cursorrules-v1.md`.
