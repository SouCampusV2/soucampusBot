# Обязательные правила сессий — BoCampus

Правила, которые действуют **каждую сессию** и имеют приоритет над удобством и
скоростью. Читать вместе с [`CLAUDE.md`](../CLAUDE.md). Основа взята из правил
SouCampus builds (`Claude/FirstTry/docs/RULES.md`) и переложена на Discord-бота.

## Как работать со мной (калибровка объяснений)

Мой уровень:
- Знаю HTML/CSS, немного JS. Синтаксис слабый — не напишу класс на JS с нуля.
- Хорошо понимаю архитектурные концепции (наследование, полиморфизм, ООП).
- Есть опыт с FlutterFlow (low-code) и немного с API.

Как объяснять код:
- **Не считать, что я знаю синтаксис JS** — показывать конкретный код из
  проекта, а не «напиши функцию, которая...».
- Архитектурные термины — смело, через аналогии с ООП.
- Больше готового кода с объяснением, что делает каждая часть; постепенно
  давать писать самому.
- Простым языком: реальный код + почему именно так, без пересказа документации.

## Правила разработки

- Простые решения там, где уместно. Сначала рабочая версия, потом улучшения.
- Изменения — постепенно, с записью в `docs/CHANGELOG.md`.
- **Весь текст, который видят пользователи в Discord, — на английском.**
  Аудитория — владельцы серверов со всего мира. Тест `ui.test.js` падает на
  любой кириллице в `src/`. Деньги — в € (как на сайте).
- **Комментарии в коде — на английском** (так написан весь существующий код;
  не смешивать). `.md`-файлы — на русском, кроме `README.md` (он для внешнего
  взгляда, на английском).
- **Без магических строк.** Префиксы `customId`, имена ролей, типы тикетов — в
  `src/constants.js`.
- **Один префикс `customId` — один файл-обработчик** в
  `src/interactions/handlers/`. Регистрация — одна строка в `TicketModule.js`.
  Исключение — связный поток с общими проверками (`ApplicationFlow.js`):
  его обработчики живут в файле потока и регистрируются оттуда же.
- **Стадия тикета — только `transitionTicket`.** Не читать
  `payment_confirmed`/`completed`, не писать `status` руками. Переход
  вернул `false` — значит нельзя (или уже сделано вторым кликом): ответить
  пользователю и выйти. Сначала переход, потом медленная работа.
- Тексты и эмбеды — в `src/embeds/templates.js`, не собирать `EmbedBuilder`
  внутри обработчиков.

## Discord API (выучено на разборе 2026-10-25)

- ⚠️ **Discord не проверяет, КТО нажал кнопку.** Кнопку в сообщении может
  нажать любой, кто видит канал. Поэтому первые строки каждого обработчика:
  достать тикет → проверить роль/личность нажавшего → только потом действие.
  Клиент — `ensureTicketClient(interaction, ticket)`, менеджер —
  `isManagerOrAdmin(member)` (оба в `utils/permissions.js`). Модалка —
  отдельная дверь: её обработчик проверяет права **заново**, проверка на
  кнопке не считается (за время, пока модалка открыта, всё могло измениться —
  пример `quoteRefusal` в `submitQuoteModal.js`).
- **Права менеджера — только `isManagerOrAdmin(member)`.** Она должна учитывать
  роль из `/setup` и право Administrator. Проверка по имени роли где-то ещё —
  ошибка того же класса, что в разборе 2026-10-25.
- **На interaction есть 3 секунды.** Если до ответа идёт что-то медленное
  (создание канала, несколько `fetch`/`send`), два способа:
  - запись в базу уже сделана → **сначала ответить** (`update`), потом слать
    уведомления (шаблон — `confirmPayment.js`);
  - результат ещё не известен → `deferUpdate`/`deferReply`, работа, потом
    `editReply` (шаблон — `confirmTicket.js`, `contactFreelancer.js`).
  Иначе «This interaction failed», хотя код отработал.
- **Ответить на interaction можно один раз.** Второй `reply` бросает ошибку.
  В `catch` — только `replyError(interaction, текст)` из `utils/replies.js`:
  он сам выбирает `reply` или `followUp`. `interaction.reply(...).catch(() => {})`
  в `catch` не писать — после `update`/`defer` он молча ничего не делает.
- **`showModal` — только первым ответом**, после `defer` его вызвать нельзя.
- **`customId` ≤ 100 символов.** Префикс + id тикета + id пользователя
  помещаются; длинные данные в `customId` не класть — класть в базу.
- **Тайм-ауты и таймеры живут в памяти и умирают с процессом.** Всё, что
  должно случиться «через N минут», записывает время в базу. Два шаблона:
  таймер + восстановление на старте (`quote_channel_due_at` +
  `recoverPendingQuoteChannels`) или обход базы по расписанию
  (`channel_delete_at` + `cleanupJob.js`) — второй проще и сам повторяет
  упавшее. Таймерам — `.unref()`: процесс держит соединение с Discord, а
  висящий таймер вешает тесты (выучено 2026-10-26).
- **Привилегированные интенты — только с записанной причиной.** Сейчас:
  `Guilds` + `MessageContent` (транскрипты; бот на одном сервере, решение
  владельца 2026-10-26). `GuildMembers` не нужен: права — из
  `interaction.member`, имена — `guild.members.fetch(id)` (REST). Интент в
  коде без галочки в Developer Portal = бот не входит («disallowed
  intents»); состояние галочек проверяется запросом
  `GET /applications/@me` (поле `flags`).
- ⚠️ **Проверять живого бота — только REST-запросами, без второго
  подключения к шлюзу** (выучено 2026-10-26). Второй `client.login()` с тем
  же токеном, пока бот работает на VPS, — это два процесса на один токен:
  нажатие в эти секунды могло уйти не туда. Для чтения данных хватает
  `fetch('https://discord.com/api/v10/...')` с заголовком `Bot <token>`.
- **`ephemeral: true` устарел** — только `flags: MessageFlags.Ephemeral`
  (тест `ui.test.js` сторожит).

## База (SQLite, `better-sqlite3`)

- **Новая колонка = `addTicketColumn(...)` в `runMigrations`** + та же колонка
  в `schema.sql` (для свежих баз). Только `schema.sql` не хватит: существующая
  база колонку не получит.
- **Индекс на новую колонку — в `runMigrations` после добавления колонки**,
  не в `schema.sql` (коммит `2f0498a`: индекс раньше колонки ронял старт).
- **Миграция перезапускаемая:** проверка «колонка уже есть» перед `ALTER`.
- **Состояние «проверил → записал» в один синхронный кусок.** Node
  однопоточный: пока между проверкой и записью нет `await`, второй клик не
  влезет. `await` посередине открывает гонку двойного нажатия.
- **Только параметры `?`**, никакой склейки пользовательского текста в SQL.
- **Миграцию с данными сначала прогнать на копии живой базы** (`db.backup()`
  в scratchpad → `initDatabase` на копии → посмотреть результат). Так
  2026-10-26 увидели, что в базе лежат «3 weeks», «Vvg», «Fff».
- Файл базы (`database/*.db`) в git не коммитится — это данные, а не код.

- ⚠️ **Настройки сервера, записанные мимо бота (скрипт в контейнере, правка
  базы), бот не увидит до перезапуска:** `GuildConfig` держит их в памяти
  процесса. После такой записи — `docker compose restart`. Через `/setup` —
  не нужно (выучено 2026-10-26).

## Отладка (перенесено из SouCampus builds, там каждое стоило дня)

- **Прежде чем чинить гипотезой — поставь три строчки лога.** Правдоподобие
  догадки о её верности не говорит ничего.
- **Починил место — проверь класс.** Нашёл ошибку в одном обработчике —
  `grep` по такому же образцу во всех остальных. Обработчики писались
  копипастой, и баги в них тоже скопированы.
- **«Вроде работает» — не доказательство.** Пустой `catch (_) {}` глотает
  ошибки: в `declineOrder.js` присваивание `const` падало каждый раз, и этого
  никто не видел. Новые пустые `catch` не писать; где глотаем — хотя бы
  `logger.debug`.

## Как проверять

- **Тесты бота — только `tests/**/*.test.js`** (так в `npm test`). Новые Node сами
  находят и `*.test.ts`; без явного пути раннер подхватил тест сайта из
  `docs/phase4/site/` и уронил CI (2026-10-27).
- **Перед коммитом:** `npm run check && npm test`. CI повторяет то же на
  GitHub; красный CI = не мёржить.
- **Баг → сначала тест, который падает**, потом правка. Тест, не увидевший
  красного, ничего не доказывает. Тесты — `tests/*.test.js`, фейки —
  `tests/helpers/`. Фейковый interaction, как и настоящий, бросает ошибку на
  втором ответе — это ловит баги «ответил дважды».
- **`node --check` и тесты не заменяют прогон в Discord.** Права каналов,
  видимость кнопок, тайм-ауты interaction — это поведение Discord, его видно
  только живьём. Поэтому есть `TEMP.md`.
- **Claude в Discord не кликает.** Управлять пользовательским аккаунтом
  скриптом (self-bot) запрещено правилами Discord. Делим так: Claude пишет
  код, тесты на логику и запускает бота, читая логи; владелец кликает по
  `TEMP.md` на тестовом сервере.
- **Чек-лист пишется, глядя в код**, а не по памяти о своих правках.
  Пересборка списка называет, что выброшено и почему. Отметки владельца
  задним числом не исправляются.
- **Проверка, которая не смогла прочитать, говорит FAIL, а не ok.**

## Документация

  `SPEC.md`) и вычёркивать везде.

## Секреты

- Токен бота — только в `.env` (в `.gitignore`). Утёк токен → сразу Reset Token
  в Developer Portal, это единственное лекарство.
- В логи токен и содержимое `.env` не печатать.

## Git

- **Автор коммитов — только пользователь. Без соавторства ИИ** (никаких
  `Co-Authored-By`).
- **Работа идёт в ветке `dev`**, проверяется на тестовом сервере, потом мёрж
  в `master`. Мёрж — отдельное осознанное действие владельца, не часть
  рутинного коммита.
- Цепочки команд — через `&&`, чтобы цепочка остановилась на первой ошибке.
- Не переписывать историю (`--amend`, force push).
