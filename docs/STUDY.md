## Зачем

BoCampus стоит в портфолио (`stavytskyi.vercel.app`, раздел More work) с
формулировкой **«Idea, order flow and features; runs on my own VPS»**. Код
писал не я, поэтому на сайте нет слова «wrote».

Цель разбора — чтобы на собеседовании я мог уверенно ответить на любой вопрос
о боте: как устроен заказ, где хранятся данные, почему двойной клик ничего не
ломает, как бот говорит с сайтом. Отказ после pair programming в Wise был
именно об этом: «сильнее база, меньше зависимости от AI».

**Готово, когда** выполнены все три пункта:
1. Пройдены модули 1–12, на каждый контрольный вопрос я отвечаю своими словами,
   без подсказки.
2. Я сам, без готового кода от Claude, написал один тест и одну маленькую
   правку (задания в модулях 11 и 12), и они прошли `npm run check && npm test`.
3. Я рассказал путь одного заказа (схема ниже) за 3 минуты вслух — Claude
   задавал уточняющие вопросы, как интервьюер.

После этого формулировку на сайте можно усилить: «designed it, run it, and

## Главная мысль за одну минуту

Бот — это программа, которая **ждёт событий** от Discord: «кто-то нажал
кнопку», «кто-то отправил форму», «кто-то вызвал команду». На каждое событие
она:

1. понимает по `customId`, **что** нажали, и находит нужный обработчик;
2. проверяет, **кто** нажал и **можно ли** ему это сейчас;
3. меняет данные в SQLite (главное — статус тикета);
4. отвечает в Discord: обновляет сообщение, создаёт канал, пишет людям.

Похоже на консольную программу, которая читает ввод в цикле, — только «ввод»
приходит событиями, а состояние между событиями живёт в базе, а не в
переменных.

## Путь одного заказа (выучить наизусть)

```
Клиент жмёт Order на панели
  └─ модалка с брифом ──────────────── тикет создан, статус FORM, свой канал клиента
Клиент дозаполняет (версия, дедлайн) → Submit order
  └─ FORM → OPEN ───────────────────── создаётся канал квот, его видят билдеры
Билдер жмёт Submit quote → модалка (цена, срок, сообщение)
  └─ строка в proposals (pending) ──── квота приходит клиенту с кнопками
Клиент: Accept / Contact (ветка) / Decline
  └─ Accept: OPEN → ASSIGNED ───────── билдер получает доступ к каналу клиента
Менеджер: Confirm Payment
  └─ ASSIGNED → PAID ───────────────── билдеру «можно начинать», кнопка Mark as Complete
Менеджер: Mark as Complete
  └─ PAID → COMPLETED ──────────────── клиенту кнопка отзыва
Клиент оставляет отзыв (один на заказ)
Закрытие: любой статус → CLOSED ────── канал в архив, только чтение, удаление через 48 ч
```

Ещё два типа тикетов: **Help** (`OPEN → CLOSED`) и **Team Application**
(`OPEN → ACCEPTED / REJECTED → CLOSED`).

## Модуль 2. Роутер и `customId`

**Файлы:** `src/core/InteractionRouter.js`, `src/constants.js` (`PREFIX`),
`src/modules/tickets/TicketModule.js`.

У каждой кнопки в Discord есть строка `customId`. Бот кладёт в неё
**что** нажато и **для какого тикета**: `confirm_payment:3f9a1c2b7d4e`.
Роутер берёт часть до первого `:` и ищет обработчик в `Map`:

```js
const prefix = getPrefix(customId);   // "confirm_payment"
const handler = handlers.get(prefix); // функция из handlers/confirmPayment.js
const parts = parseCustomId(customId); // ["confirm_payment", "3f9a1c2b7d4e"]
await handler(interaction, parts);
```

Регистрация — одна строка на кнопку в `TicketModule.js`:
`registerHandler(PREFIX.CONFIRM_PAYMENT, handleConfirmPayment);`

Аналогия из ООП: это паттерн «команда» / таблица диспетчеризации. Вместо
длинного `if/else` по всем кнопкам — словарь «имя → функция».

**Упражнение:** найди в коде, какой файл обработает `decline_quote:abc:42:price`
и что значат три части после префикса.

## Модуль 3. База данных

**Файлы:** `database/schema.sql`, `src/core/Database.js`.

SQLite — база в одном файле. Библиотека `better-sqlite3` **синхронная**: запрос
выполняется сразу, без `await`. Это важно в модуле 4.

Главные таблицы:

| Таблица | Что хранит |
|---|---|
| `tickets` | тикет: тип, статус, клиент, каналы, билдер, дедлайн, номер #N |
| `ticket_fields` | ответы формы как пары «поле — значение» |
| `proposals` | квоты билдеров: цена, срок, статус pending / accepted / declined |
| `reviews` | отзывы: оценка, текст, согласие показать на сайте |
| `conversations`, `conversation_messages` | переписка билдер ↔ клиент |
| `guild_config` | настройки сервера из `/setup` |
| `action_log` | кто что сделал |
| `site_outbox` | очередь отправки на сайт (модуль 11) |

Три функции на всё: `query` (много строк), `get` (одна), `run` (изменить).
Всегда с параметрами `?`, никогда не склеивая текст пользователя в SQL — это
защита от SQL-инъекций.

**Миграции:** новая колонка добавляется в `runMigrations`, а не только в
`schema.sql`. `CREATE TABLE IF NOT EXISTS` не добавит колонку в уже
существующую таблицу на VPS.

## Модуль 4. Статусы тикета (самый важный)

**Файл:** `src/modules/tickets/TicketStatus.js`, 146 строк.

Стадия тикета — **одна колонка `status`**. Куда из какой стадии можно
перейти — таблица:

```js
const TRANSITIONS = {
  order: {
    open:      ['form'],
    assigned:  ['open'],
    paid:      ['assigned'],
    completed: ['paid'],
    closed:    ['form', 'open', 'assigned', 'paid', 'completed'],
  },
  ...
};
```

Читается так: «в `paid` можно попасть только из `assigned`».

Переход делает одна функция `transitionTicket`, и в ней главный трюк проекта:

```sql
UPDATE tickets SET status = 'paid' WHERE id = ? AND status IN ('assigned')
```

Проверка «можно ли» и запись — **один запрос**. Если менеджер нажал Confirm
Payment дважды, первый запрос поменяет 1 строку, второй — 0 (статус уже
`paid`), и функция вернёт `false`. Двойной клик физически не проведёт оплату
дважды.

Это **конечный автомат** (state machine). На интервью так и говорить.

**Упражнение (на бумаге):** заказчики платят 50/50. Как добавить стадию
«оплачена первая половина»? Ответ: новая строка в `TRANSITIONS`, а не новый
флаг в таблице. Почему так лучше?

## Модуль 5. Права: каждая кнопка — публичная дверь

**Файл:** `src/utils/permissions.js`.

Discord **не проверяет, кто нажал кнопку**. Кнопку Confirm Payment может
нажать любой, кто видит сообщение. Поэтому первые строки **каждого**
обработчика — проверка «кто ты»:

```js
// клиент этого тикета?
if (ticket?.client_id === interaction.user.id) return true;

// менеджер? — право Administrator или роль из /setup
if (member.permissions?.has(PermissionFlagsBits.Administrator)) return true;
const configured = roleIdsSetting(member.guild.id, 'role_manager');
return configured.some((id) => member.roles.cache.has(id));
```

Модалка (всплывающая форма) — отдельная дверь: её обработчик проверяет
права **заново**. Пока форма была открыта, всё могло поменяться.

Полная карта «кто что может» — `docs/ARCHITECTURE.md` → «Безопасность —
карта дверей».

**Контроль:**
- Почему менеджер определяется по ID роли, а не по имени «Manager»?
- Билдер открыл модалку квоты, а клиент за это время выбрал другого билдера.

## Модуль 6. Тикет и форма заказа

**Файлы:** `src/modules/tickets/openTicket.js`,
`src/modules/tickets/flows/OrderFlow.js`, `src/embeds/templates.js`.

Создание тикета — приватный канал. Права задаются списком «перезаписей»:

```js
{ id: guild.id, deny: ViewChannel },                       // все остальные не видят
{ id: user.id,  allow: ViewChannel | SendMessages },       // клиент видит и пишет
// + каждая роль менеджера: видит и пишет
```

Потом строка в `tickets`, приветственная карточка и пинг команды.

Форма заказа — модалки (у Discord в одной модалке максимум 5 полей, поэтому
две). Обязательные поля — `REQUIRED_ORDER_FIELDS` в `constants.js`. Кнопка
**Submit order** (`handleSubmitOrder`):
1. проверяет, что жмёт клиент;
2. проверяет, что все обязательные поля заполнены;
3. делает переход `FORM → OPEN` — он же защита от двойного клика;
4. создаёт канал квот, который видят все роли билдеров и менеджеров, и кладёт
   туда бриф и референсы.

**Правило 3 секунд.** На любое нажатие Discord ждёт ответа 3 секунды, иначе
показывает «This interaction failed». Поэтому сначала быстрый ответ
(`update`, `deferReply`), потом медленное: создание каналов и рассылки.

## Модуль 7. Квоты и выбор билдера

**Файлы:** `src/modules/proposals/ProposalRepository.js`,
`src/interactions/handlers/submitQuote*.js`, `selectFreelancer.js`,
`contactFreelancer.js`, `declineQuote.js`.

Квоту можно отправить, только если (`quoteRefusal`): заказ в статусе `open` и
у этого билдера нет другой ожидающей квоты на этот заказ.

Клиент жмёт **Accept** → `selectFreelancer.js`. Все проверки и запись идут
**до первого `await`**:

```js
if (ticket.client_id !== interaction.user.id) { ... }   // только клиент
const proposal = proposals.find(... status === 'pending');
if (!acceptProposal(proposal.id, ticketId, freelancerId)) { ... } // OPEN → ASSIGNED
await interaction.update(...);   // ответ
// дальше медленное: дать билдеру доступ к каналу клиента, кнопка оплаты менеджеру
```

**Contact** открывает приватную ветку для разговора до выбора. Нюанс Discord:
в ветку пускают только тех, кто видит канал-родитель, поэтому сначала права
на канал, потом добавление в ветку.

## Модуль 8. Оплата, сдача, отзыв, закрытие

**Файлы:** `confirmPayment.js`, `markComplete.js`, `submitReview*.js`,
`closeTicket.js`, `modules/tickets/closing.js`, `jobs/cleanupJob.js`,
`commands/takeCommand.js`.

Оплата подтверждается **вручную менеджером** (PayPal / Wise-инвойс по ссылке,
`/paylink`). Бот денег не трогает — только фиксирует факт. `confirmPayment.js`
— эталон обработчика, разобрать построчно:
проверка менеджера → тикет → переход `ASSIGNED → PAID` → запись в журнал →
ответ → уведомления клиенту, в канал квот и билдеру в ЛС.

`/take` — менеджер берёт заказ сам, без квот (пока нет команды билдеров). Это
тот же переход `OPEN → ASSIGNED`.

Закрытие: статус `CLOSED`, канал в архив только для чтения, в базу —
`channel_delete_at` через 48 часов. Удаляет не таймер, а фоновая задача
(модуль 10). Менеджер может нажать Keep — тогда не удалять.

## Модуль 9. Шина событий

**Файлы:** `src/modules/tickets/events.js`, `OrderCard.js`, `StaffLog.js`,
`Transcript.js`, `modules/clients/ClientTiers.js`.

`transitionTicket` после успешного перехода делает
`ticketEvents.emit('status', {...})`. На это событие подписаны:

Это паттерн **Наблюдатель** (Observer / pub-sub). Новая реакция на смену
статуса — новый слушатель, а не правка в каждом обработчике.

## Модуль 10. Таймеры и фоновые задачи

**Файлы:** `src/jobs/deadlineJob.js`, `cleanupJob.js`, `backupJob.js`,
`src/utils/dates.js`.

| Задача | Когда |
|---|---|
| Напоминания о дедлайне | каждый день в 09:00 по Таллину (cron) |
| Удаление каналов закрытых тикетов, напоминание о брошенной форме | каждые 10 минут, обход базы |

Главное правило: **таймер в памяти умирает вместе с процессом.** Всё, что
должно случиться «потом», записывает время в базу, а задача по расписанию
проверяет базу. Перезапуск ничего не теряет, упавшее повторится.

`parseDeadline` превращает «25.12.2026» или «in 2 weeks» в `YYYY-MM-DD`.

## Модуль 11. Связь с сайтом

**Файлы:** `src/modules/site/SiteBridge.js`, `consent.js`, `docs/PHASE4.md`.

Два направления:

1. **Бот → сайт.** С согласия клиента отзыв и черновик работы для портфолио
   уходят на soucampus.online. Это не прямой запрос, а **очередь**
   (`site_outbox`, паттерн Outbox):
   - запись кладётся в таблицу;
   - фоновая отправка пробует доставить;
   - при ошибке повторяет с растущей паузой (exponential backoff: 2, 4, 8…
     минут, с потолком) и сдаётся после N попыток;
   - каждый запрос **подписан** HMAC-SHA256 с общим секретом и временем:
     ```js
     createHmac('sha256', secret).update(`${timestamp}.${body}`).digest('hex')
     ```
     Сайт пересчитывает подпись и отбрасывает чужие и старые запросы.
2. **Сайт → Discord.** Сайт постит новые карты через вебхуки каналов
   (`/setup site_channel` выдаёт вебхук), бот ставит реакции под постами.

**Статус:** код готов, но мост бот → сайт на VPS ещё не включён
(`OWNER-TASKS.md`, п. 8).

**Своё задание (часть критерия «готово»):** написать тест в

## Модуль 12. Тесты, CI, деплой

**Файлы:** `tests/*.test.js`, `tests/helpers/fakes.js`, `tests/helpers/db.js`,
`.github/workflows/ci.yml`, `Dockerfile`, `docker-compose.yml`,
`docs/DEPLOY.md`.

Тесты не ходят в Discord. Вместо него — **фейки**: поддельные сервер, роли,
каналы, нажатие. База — в памяти. Пример из `tests/lifecycle.test.js`:

```js
test('a manager with a custom-named role can confirm payment', async () => {
  const s = setup('g-life-pay');
  const i = fakeInteraction({ client: s.discord, member: s.manager, guild: s.guild });
  await handleConfirmPayment(i, ['confirm_payment', s.ticketId]);
  assert.equal(answerKind(i), 'update');                      // ответил на нажатие
  assert.equal(getTicketById(s.ticketId).payment_confirmed, 1); // записал в базу
  assert.equal(s.clientChannel.sent.length, 1, 'client was told');
});
```

Запуск: `npm run check && npm test`. CI на GitHub Actions повторяет то же на
Node 22 и 24 на каждый push.

Деплой: VPS, Docker-контейнер, автоперезапуск, сервер сам тянет код из
GitHub по ключу только для чтения. Подробно — `docs/DEPLOY.md`.

**Своё задание (часть критерия «готово»):** маленькая правка с тестом.
Например, в ответе `/take` на заказ, у которого уже есть билдер, подсказка
«use /paylink» (`CLAUDE.md` → «С чего начинать», п. 3). Порядок: тест,
который падает → правка → тест проходит → коммит в `dev`.
